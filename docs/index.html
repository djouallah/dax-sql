Limitations

dax-sql returns the same answers as Power BI, except in the cases below. All of them are by design: dax-sql follows plain SQL rules there, not Power BI's. They are not bugs, and they will not be "fixed".

By design, always

  1. Text is case-sensitive. "Red" and "red" are two different values. Power BI treats them as one.
  2. Text sorts by the engine's rules. On DuckDB that is character code order, not Power BI's language-aware order.
  3. Trailing spaces count. "a " and "a" are two different values. Power BI removes trailing spaces when it loads data.
  4. There is no blank row. Every key in a fact table must exist in its dimension. A sale whose key is missing from the dimension still counts in the total, but appears under no value of that dimension.
  5. A column that mixes numbers and text comes back as text.
  6. IFERROR returns its first argument. SQL has no error values.
  7. Values come back unformatted. Applying a measure's format string is up to you. FORMAT works in English (en-US) with a fixed pattern only.

By design, on Microsoft Fabric (T-SQL) only

  1. 1 / BLANK() is blank, not infinity. T-SQL has no infinity.
  2. Sums of floating-point numbers are computed exactly, so they can differ from Power BI's in the last digit.
  3. PATH functions are not available. Fabric has no recursive queries.

Not supported

Anything not listed in DESIGN.md. dax-sql then stops with an UNSUPPORTED error. It never returns a guessed answer.

A measure is a question, not a formula

In Power BI a measure is written once, [Sales Amount] := SUM(Sales[Amount]), and then asked everywhere: in a total, in a row per year, under a slicer, inside another measure. What it returns depends on where it is asked: on the filters around it, which DAX calls the filter context. SQL has no filter context, no relationships between tables, and no rows that turn into filters. So one measure is different SQL in every place it is used. Parse: the text becomes a tree

The lexer and parser know DAX's grammar and nothing else. [Sales PY] is a name in brackets: whether it is a measure, and what it means, is the compiler's question. The tree below is this page's parser output.

Compile: the filter context as a value

The compiler walks the tree with an environment: the filter context, the row contexts, the variables, the columns SUMMARIZECOLUMNS groups by, the shadow contexts ALLSELECTED restores, and the measures being expanded. A measure reference is replaced by its expression under the current context. Wherever DAX would change the context at run time, a new one is built here, at compile time.

A filter is one of three things

KindWhat it saysMade by
bindA column equals a value, possibly an outer row's: the SQL is then correlated.A group's key; context transition
predA predicate on columns, read on each row.CALCULATE(…, T[c] > 5)
relThe rows of a table, matched on its columns' lineage.TREATAS, VALUES, FILTER, time intelligence

A filter reaches a table only along relationships: expand(T) is DAX's expanded table (the tables T reaches through many-to-one relationships), and inbound(T) the bidirectional and many-to-many ones through which a filter enters from outside, as a semi-join.

CALCULATE, in four steps

  1. Evaluate the filter arguments in the outer context.
  2. Turn the row contexts into binds: context transition.
  3. Apply the relationship modifiers (USERELATIONSHIP, CROSSFILTER), then the removals (ALL, REMOVEFILTERS).
  4. Drop what the context said about the filters' columns, unless KEEPFILTERS, and add the filters.

Here

[Sales PY] is CALCULATE([Sales Amount], SAMEPERIODLASTYEAR('Date'[Date])). In a month's row the context binds 'Date'[Year] and 'Date'[Month]. SAMEPERIODLASTYEAR is a rel filter: the dates of that month, one year earlier. A filter on a date table's date column clears the rest of that table, so the year and month binds go, and only those dates stay.

Plan: a few node kinds

The compiler's output is a tree close to relational algebra. Every aggregate is an agg over a scan of one model table under one filter context. freeRows(x) says which rows from outside a node it reads: that is exactly the correlation its SQL will need.

Emit: correct first, then fast

Written straight from the plan, each measure on each row is a correlated subquery: exactly what DAX means, and slow on real data. The emitter then rewrites it. Fusion: aggregates over the same table, keys and filters become one GROUP BY CTE, joined to the groups. Totals from groups: a subtotal adds up a group's rows instead of scanning again. Grouping before joins: a fact is grouped by its key before it meets its dimensions. Mappings for time intelligence: each group's dates are computed once and joined. optimize: false turns them all off. Here the rewritten SQL is longer, not shorter: length is not the point, correlation is. Rewrites off, each measure is a subquery evaluated for one month at a time, which the engine must decorrelate (DuckDB does; Fabric runs some as loops) and which is still slow at scale (the table below). Rewrites on, each is a GROUP BY over all the months at once, and the dates each month maps to are computed once and joined: no subquery is left per month.

Dialect: the spelling of one engine

The plan and the rewrites are the same for every engine; a dialect says how to write them. DuckDB is the default. dialect: 'tsql' writes T-SQL for Fabric's SQL analytics endpoint and Warehouse: a boolean is a BIT, OUTER APPLY stands for LATERAL, a CASE inside an aggregate for FILTER, and some subqueries take shapes Fabric decorrelates rather than loops over. To add an engine, extend Dialect in src/dialects/base.js.

About

dax-sql is a compiler for semantic models. A DAX query, or an Apache Ossie SQL query, goes in, with a Power BI (TMSL) or Ossie model. One SQL SELECT comes out, for DuckDB or Microsoft Fabric. It has no dependencies and is MIT licensed. It was initially written by N.S. Devaraj.

npm install dax-sql
import { createCompiler } from 'dax-sql';
import { tmslToModel } from 'dax-sql/formats/tmsl.js';   // or formats/ossie.js

const model = tmslToModel(JSON.parse(bimText));           // a model.bim
const dax = createCompiler(model, { tableSource: t => `read_parquet('data/${t.name}.parquet')` });
const { sql, columns } = dax.compile(`EVALUATE SUMMARIZECOLUMNS('Date'[Year], "Sales", [Sales Amount])`);

The full design, with every rule it implements, is in DESIGN.md.
